## Vision

Maestro is a standalone menu bar app that serves as muwav's network-facing
companion. It enables muwav to ship with **zero network entitlement** — all
networking is opt-in via Maestro.

The privacy pitch is absolute and it writes itself:
*"muwav has no network access. None. Your music stays yours."*
Delete Maestro = fully isolated music player. Consent-based networking:
users opt IN to connectivity, not out.

## Responsibilities

*	**Update replacement**: consume the existing MUW-344 distribution
	pipeline (manifest + DMG on Bunny CDN), download signed+notarized
	bundles, replace `muwav.app` atomically. Cannot patch files inside
	the bundle — signature invalidation means whole-bundle replacement
	only.
*	**XPC bridge**: network proxy for anything muwav needs from the
	outside world — Bonjour advertisement for iOS discovery, remote
	command relay, RemoteLog, future features.
*	**Menu bar presence**: lightweight status indicator, manual "check
	for updates" trigger.

## What changed since this ticket was written (2026-05-28)

*	**MUW-146 (stopgap banner) shipped and is live.** `UpdateChecker.swift`
	(`Shared/Updates/`, line 30) polls
	`https://muwav.surf/updates/latest.json`; manifest fields are
	`{advertise, latest, minimum, dangerous}` (integer build numbers,
	no semver; `advertise` is the soft-nudge lever). Banner action opens
	`/changelog` in the browser — user installs manually. Maestro
	upgrades this from "notify" to "replace."
*	**MUW-344 built the full macOS distribution pipeline.** `release.py`
	stage/promote/recall, Bunny CDN (`muwav.b-cdn.net`), Developer ID
	signing under Cedar Syntax LLC (Team `F252L9GUBW`), notarized +
	stapled DMG, manifest deployed to muwav.surf. Maestro is a
	*consumer* of this pipeline, not a replacement for it.
*	**MUW-26 (dual-build: network vs no-network) was cancelled** in favor
	of this architecture — one build, always zero-network, Maestro as the
	opt-in companion.
*	**MUW-324 (iOS stand-alone mode) is now the #2 post-launch priority.**
	The iOS remote story and Bonjour discovery must be reconciled with
	that ticket's direction before Maestro's XPC surface is locked.

## Recon prompt (Cici — Fable protocols: carry straight through Recon → Solutioning → Implementation)

1.	**Inventory muwav's current network surface.** Entitlements files for
	the macOS target, `Shared/Updates/`, all Bonjour/remote-control code
	paths, and anything else that touches the network. Produce the
	definitive list of what must migrate to Maestro for muwav to drop
	the network entitlement entirely. Write findings to
	`docs/fakear/attach/MUW-145/`.
2.	**Verify the CloudKit assumption.** The vision rests on "CloudKit
	sync works via cloudd with no app network entitlement." Confirm this
	empirically or from authoritative documentation — if it's false, the
	whole zero-network story changes and that verdict must be loud.
3.	**XPC architecture.** launchd agent with Mach service vs direct
	`NSXPCConnection` to a running menu bar app; code-signing
	requirements between the two processes (same team, hardened
	runtime); what happens when Maestro isn't installed (muwav must
	degrade gracefully to fully-offline, no error surfaces).
4.	**Atomic bundle replacement.** Constraints: muwav running during
	replacement, quarantine/Gatekeeper, app translocation, signature
	verification of the downloaded DMG before swap. How `release.py`
	artifacts and `latest.json` feed the flow. EdDSA or rely on Apple's
	notarization + signature checks?
5.	**Implementation language verdict.** Original vision was a Rust
	binary (single executable, no runtime). Recon must check XPC
	ergonomics from Rust honestly — NSXPC is ObjC-native, and a Swift
	menu bar app may be the pragmatic call. Name the tradeoff; R
	decides at DAT.
6.	**Maestro's own distribution.** Separate download vs shipped inside
	muwav.app initially. Note: Maestro updating *itself* is the same
	hard problem one level down — design so it rarely needs to.
7.	**Reconcile with MUW-324.** Read that ticket. If iOS stand-alone
	changes what discovery/relay Maestro must serve, record the
	dependency rather than guessing.

## Not doing

*	No changes to the shipped stopgap banner as a side effect — it stays
	the fallback for users who never install Maestro.
*	No new manifest schema unless recon proves the current one can't
	carry the replacement flow — extend `latest.json`, don't fork it.
*	No touching the multicast entitlement question until its approval
	status is confirmed (filed 2026-05-26; status unknown — R to
	confirm).
